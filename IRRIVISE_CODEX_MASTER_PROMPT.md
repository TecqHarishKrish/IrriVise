## 1. Product decision: what to build

### The choice

Build a **desktop-first, fully responsive web application** that also works on tablets and phones. Use a React + TypeScript frontend and Python FastAPI backend. Provide an optional installable PWA shell after the core app passes tests. The main application does not depend on being installed.

**Why a web app beats a native phone/desktop app for this project:** RL training is CPU-heavy and belongs on the local/server Python backend. A browser provides multi-page visualizations, data forms, graphs, and experiment inspection without distributing platform-specific builds. It is cheaper to maintain and easier to present at a final-year project demonstration. Streamlit remains available as an **optional separate researcher prototype**, not the main UI; the final UI must be crafted React, not a bare Streamlit dashboard.

### Users and product goals

- **Student/researcher:** Configure simulations, train models, run comparative experiments, evaluate results, export plots/data.
- **Agricultural user/demo audience:** Understand current simulated field status, irrigation suggestions, uncertainty, and expected implications with minimal jargon.
- **Project evaluator:** Inspect data provenance, methodology, training status, baselines, limitations, and reproducible outputs.

**Success means:** a user can install dependencies, start one command for the UI/API/worker, choose a dataset, create a field scenario, run a simulation, inspect recommendations, train PPO on a feasible CPU preset, compare CARAT against baselines, and export reproducible results; every numerical result is traceable to a run and clearly labeled.

## 5. Domain objects, units and database schema

Use SQLAlchemy + Alembic for metadata; high-volume daily traces live as Parquet/CSV on disk with references in SQLite. Use canonical units internally.

### Entities

1. `Project`: id, name, description, crop, creation date, archive status.
2. `FieldScenario`: id, project_id, name, location lat/lon, crop variety/profile, soil profile, planting/harvest dates, irrigation max daily mm, seasonal irrigation budget mm, observation budget integer, season identifier, config JSON, validation status.
3. `WeatherDataset`: id, source (`nasa_power` / `sample` / `uploaded`), coverage, coordinates, time standard, parameter units, missingness, checksum, file path, license/provenance, created time.
4. `TrainJob`: id, type, owner project/scenario, status, progress, cancel_requested, start/finish, seed, hyperparameters JSON, log/artifact paths, error summary.
5. `ModelRecord`: id, experiment linkage, algorithm, training configuration checksum, checkpoint path, seed, step count, validation metrics, provenance, created time.
6. `SimulationRun`: id, scenario_id, controller kind, model_id optional, weather dataset/split, status, start/end, seed, config checksum, result artifact paths, summary metrics, error description.
7. `ExperimentGroup`: id, name, locked shared evaluation setup, run identifiers, status, comparison artifact.
8. `ObservationEvent`: run_id, day, was_requested, measurement (if taken), noise params, remaining budget, estimated VOI, triggered reason — store daily trace rather than huge SQL tables if faster.
9. `ExportRecord`: path, requested format, source run/group, generated date, checksum.

### Units and invariants

- Irrigation, rainfall, ET₀, runoff, deep drainage: **mm per day**; soil-water storage: **mm per root zone**; volumetric water content: **m³/m³**; root depth: **m**; crop yield: **t/ha**; water productivity: **kg/m³**.
- Convert volumetric water content to root-zone storage carefully: `storage_mm = theta_m3m3 * root_depth_m * 1000`, accounting for multi-layer roots if implemented.
- `wilting_point < field_capacity < saturation`; `0 <= rainfall`, `0 <= irrigation <= max_daily`; seasonal applied irrigation never exceeds budget; `0 <= observations_used <= observation_budget`.
- Persist native source units and conversions. Record whether each quantity is modeled, measured, forecast, or simulated truth.
- Validate crop dates, soil bounds, season length, location coordinates, unknown categories, malformed CSV, NaNs, infinities and empty files at boundaries. Avoid silent clipping that hides invalid input; if physically meaningful projection is needed, record it.
- Config schema for every experiment must be serializable and hashable, with seed, code revision/commit, package versions, data checksum, model checkpoint checksum, and time standard.

## 6. Weather, crops and core scientific environment

### 6.1 Data source: NASA POWER, with offline sample

Implement official NASA POWER **daily** point API with a configurable latitude, longitude, start/end date, and requested parameters. Investigate/verify these source parameter names and their units: `T2M_MAX`, `T2M_MIN`, `PRECTOTCORR`, `ALLSKY_SFC_SW_DWN`, `WS2M`, `RH2M`. Add ET₀ from a documented, validated FAO-56 calculation using all required inputs or a documented suitable source; **do not confuse actual evapotranspiration with reference evapotranspiration**.

Use an explicit time standard (UTC or local solar time) and store it; NASA POWER daily defaults may differ. Cache source responses by query including coordinates/date/parameters; honor request limits, bounded retry, timeouts, network errors and rate limiting. Never send unbounded repeated API calls. Fail transparently and offer local sample dataset mode. API keys must not be required.

Preprocessing must check daily continuity, null/missing sentinels, duplicate dates, `Tmin <= Tmax`, radiation/rainfall bounds, missingness percentages, source date coverage, units; never impute test-series missingness using future realized test values. Convert output to AquaCrop-compatible weather dataframe and a standardized core schema. Ensure train/validation/test split by **whole historical growing seasons in chronological order**, not randomly by day.

Default start: maize, a documented Tamil Nadu location selected in the UI, a sandy-loam profile. For offline bootstrapping use a short **synthetic weather fixture labeled "synthetic demonstration"**, and make genuine NASA POWER ingestion a first-class flow.

### 6.2 AquaCrop-OSPy integration

Create an `AquaCropAdapter` with a clear public interface to configure weather, soil, crop, irrigation schedule, run and extract water/yield data. Start with published examples and documented maize/soil defaults, not invented agronomic parameters.

- Validate no-irrigation, fixed schedule, and threshold baseline cases.
- Current AquaCrop-OSPy provides an irrigation management class supporting rainfed, soil-moisture target, interval, scheduled, net irrigation and constant-depth modes. Verify exact signatures against installed version.
- For **predefined schedules**, use the supported `IrrigationManagement` schedule API.
- For **interactive daily decisions**, inspect and test the current `run_model(num_steps=1, initialize_model=...)` behavior and state effects. **Do not assume that editing a schedule mid-run correctly updates irrigation without testing.** If interactive AquaCrop action injection is unreliable, use the validated fast daily simulator for RL/training; evaluate candidate **precomputed per-season schedules** in AquaCrop. Never present the surrogate as directly crop-model-calibrated if it is not.
- Provide tests comparing water use and soil-state responses for control inputs and that AquaCrop output is finite and realistic within configured ranges.

### 6.3 Daily CPU-efficient training simulator

Implement an explicit daily root-zone water-balance model (units mm):

```text
S_(t+1) = clamp(S_t + P_eff(t) + I(t) - ET_actual(t)
                - runoff(t) - deep_drainage(t), S_min(t), S_max(t))
```

Carefully define initial capacity, infiltration/rainfall partition, ET response to crop development and soil stress, evolving root depth, drainage/runoff, rainfall timing, crop stress index and observation generation. **Do not simply clamp every component and silently violate mass balance.** Log mass-balance residual and reject if outside tolerance. If you calculate stress/yield proxy, label them and validate trends against AquaCrop scenarios.

Split the hidden `ReferenceFarm` from `EstimatedDigitalTwin`:
- `ReferenceFarm.step(action_mm, realized_weather)` changes hidden truth and generates evaluation-only outputs.
- `EstimatedDigitalTwin.predict(available_forecast, applied_action)` propagates belief and uncertainty without seeing realized future rainfall.
- `SensorGateway.measure(run_id, day)` returns noisy current root-zone measurement only if observation is allowed, charges the budget atomically and records an event.

Historical realized weather is revealed to the reference simulator **after the daily action** and may enter agent history only on following days. The agent can see a legitimate *forecast*, not actual future rain. Build a forecast-error generator from training seasons / controlled noise models; never copy realized rain into forecast.

### 6.4 Simulated observation and state correction

A simulated soil sensor returns `z_t = theta_true_t + epsilon_t`, with `epsilon_t` drawn from documented noise model. Test std dev `0.01`, `0.02`, `0.04 m³/m³`, plus missing/stuck/bias scenarios. Keep random draws reproducible by seed. Validate impossible measurements and record filtered/rejected observation flags.

Start with a 1D Kalman-style correction with predicted variance `P`, measurement variance `R`, gain `K=P/(P+R)`, corrected estimate `mu'=mu + K(z-mu)`, variance `P'=(1-K)P`, with proper handling of `P=R=0`; optionally move to an ensemble filter for multi-dimensional soil states. Correct root-zone estimates, not post-run truth. Maintain uncertainty growth when observations are skipped.

## 7. Reinforcement learning design (PPO)

### 7.1 Gymnasium environment

Implement `IrrigationEnv(gym.Env)` with `reset(seed, options) -> (obs, info)` and `step(action) -> (obs, reward, terminated, truncated, info)` plus registration and `stable_baselines3.common.env_checker.check_env`. Seed NumPy, Gymnasium, PyTorch and experiment-specific random generators. A single episode equals one growing season.

**Action space initially:** `Discrete(5)` representing irrigation `[0, 5, 10, 15, 20] mm/day`. Use deterministic feasible-action projection when seasonal/daily budgets limit proposals; log proposed vs applied action.

**Observation vector** (normalized; fixed shape, documented ranges):

| Feature | Notes |
|---|---|
| estimated root-zone water / water depletion | NEVER hidden reference truth |
| uncertainty mean/std or confidence bound | from twin belief |
| day-of-season / stage encoding | cyclical or normalized |
| recent *observed* rainfall history | past only |
| forecast rain / ET₀ | generated forecast, not realized future |
| observed temperature / atmospheric demand | current available values only |
| remaining irrigation water budget | normalized, includes already applied water |
| remaining soil observations | normalized, where appropriate |
| days since last measurement | bounded, normalized |
| optional crop stress estimate | from estimated twin, not hidden truth |

Choose either `Box` vector and `MlpPolicy`, or `Dict` with `MultiInputPolicy` correctly; default `Box` is easiest. Use observation normalization fitted from training data, frozen on validation/test. Do not normalize using hidden test seasons.

### 7.2 Reward objective and control constraints

Implement a properly normalized decomposed reward, stored in `info` and run trace:

```text
r_t = -lambda_w * normalize(irrigation_mm)
      -lambda_s * normalized_water_stress
      -lambda_v * violation_penalty
      -lambda_o * observation_cost_if_jointly_controlled

r_terminal += lambda_y * normalized_yield_proxy
```

Suggested **starting weights** `water=0.2`, `stress=1.0`, `violation=2.0`, `observation=0.1`, `terminal_yield=5.0`; weights must be configurable and tuned on validation data. Hard water budgets must be enforced separately (penalties alone are insufficient). If CARAT observes outside of PPO, do not penalize PPO for an observation it never controlled; evaluate observation cost at experiment objective layer instead.

A slow/complex AquaCrop simulation may not expose true yield every fast step; define a justified terminal **yield proxy** for PPO and externally validate policy using AquaCrop yields. Do not train against future actual yield that would be unknown online.

### 7.3 Baseline PPO parameters and controlled tuning

```yaml
algorithm: PPO
policy: MlpPolicy
action_mm: [0, 5, 10, 15, 20]
learning_rate: 0.0003
n_steps: 1024
batch_size: 64
n_epochs: 10
gamma: 0.99
gae_lambda: 0.95
clip_range: 0.2
ent_coef: 0.01
vf_coef: 0.5
max_grad_norm: 0.5
net_arch: [64, 64]
device: cpu
seed: 42
```

Create *three CPU-aware presets*:
- **Quick smoke:** 2k–10k timesteps, 1 seed, very few seasons. For functional testing only; explicitly **not research-quality**.
- **Standard CPU:** 100k–300k steps, 3 seeds, periodic validation and early stopping. Time depends on hardware.
- **Research CPU:** 300k–1M+ steps if feasible, >=5 seeds, weather randomization, robust scenarios, checkpoint and evaluation, compute budget caps.

Tune only on training+validation; **never select hyperparameters based on test results**. Optuna optional with a reproducible seeded sampler, capped trials/runtime, and tuned candidate dimensions e.g. learning rate `1e-5..1e-3`, steps `[512,1024,2048]`, batch `[32,64,128]`, gamma `[0.95,0.99,0.995]`, entropy `[0,0.001,0.01]`, layers `[64,64]`/`[128,128]`, stress/water weights only within documented ranges. Avoid all-at-once combinatorial search. Use eval callback to choose checkpoint on validation episodes; no unbounded training defaults.

Training features: detailed run manifest, TensorBoard (optional) and progress events, train/validation score separation, invalid observation metrics, numerical blow-up check, ability to resume verified compatible checkpoints, graceful cancellation, deterministic repeated tests, seed isolation, optional vectorized environments after benchmark, CPU-memory caps and configurable concurrency. Implement save/load and predict smoke test.

### 7.4 Generalization and edge cases

During training expose **controlled** domain randomization: different rain patterns, dry/wet seasons, permitted soil hydraulics, uncertain initial moisture, forecast noise, sensor delay/missingness, limited budgets. Keep physical ranges valid. Acknowledge that robustness in simulated distributions does **not** imply field reliability.

Evaluate unseen weather seasons, drought-like sequences, heavy rain, unexpected missed rainfall, sensor noise/bias/dropout, low budgets, saturated soil, very dry soil, near-harvest stage, changing root depth, missing data, model mismatch and a no-remaining-observation case. Always compare to the same scenario and baseline budget.

## 8. CARAT implementation: the project's proposed research method

**Full name:** Counterfactual Action-Regret and Adaptive Twin Correction. CARAT is **proposed** by this project, not a pre-validated published algorithm. Keep the implementation modular so its individual contributions can be ablated.

### 8.1 Uncertain belief state

The twin stores a belief distribution (a bounded ensemble initially `K=20` plausible soil-water states), with model-specific weights `w_k` summing to one. Vary process noise, forecast error and soil parameter uncertainty; reject implausible states. Maintain an estimate, uncertainty interval, and observation age. Keep forecast ensemble separate from hidden realized weather.

### 8.2 Candidate irrigation action evaluation

For each plausible state `s_k` and each candidate feasible irrigation action `a ∈ {0,5,10,15,20}` mm, predict **same-horizon, same-objective** short-run value `Q_hat(s_k, a)` using the lightweight simulator and, where possible, a terminal/bootstrap value from the PPO critic or documented rollout policy. Make horizon e.g. 3–7 days configurable. Do not use future realized weather or a value function illegally trained on the held-out season. Report the approximation assumptions and bound evaluation computation per day.

Compute the information-constrained action `a_belief = argmax_a Σ_k w_k Q_hat(s_k,a)` (or compare to PPO action explicitly); compute state-informed benchmark `a*_k = argmax_a Q_hat(s_k,a)`. Define nonnegative estimated expected action regret:

```text
Regret_before = Σ_k w_k [ Q_hat(s_k,a*_k) - Q_hat(s_k,a_belief) ]
```

This is **estimated** regret, not realized oracle regret. If the estimate can become negative due to numerical artifacts, log the discrepancy and apply only a documented tolerance for floating point noise; do not paper over major model bugs. Store candidate-action ranking and predicted regret for user inspection.

### 8.3 Decision-aware observation value

Before measuring, draw `M` hypothetical possible sensor readings from the predictive observation model `p(z|belief)` with a seeded generator. For each sample reading `z`:

1. Update the belief with the assumed sensor noise.
2. Recompute the preferred irrigation action on the updated belief.
3. Estimate regret of that post-observation action using the **pre-observation uncertainty distribution conditional on the hypothetical measurement**.

Calculate:

```text
ExpectedRegretAfter = average_z(Regret_after_z)
GrossVOI = Regret_before - ExpectedRegretAfter
NetVOI = GrossVOI - observation_cost - budget_shadow_price
```

`observation_cost` is a **modeled resource cost** in consistent reward units, not a real payment or purchased sensor. Introduce a configurable **budget shadow price** or reserve rule that discourages exhausting all observations early; tune it on validation seasons only. **Observation request:** choose observe only when the estimate supports `NetVOI > threshold`, the remaining count is positive, and measurement is available. Add a clear fallback when `K`/`M` are too computationally expensive or the posterior becomes degenerate.

Important: "uncertainty high" is not identical to "new measurement valuable". If all plausible states select the same action and estimated regret is near zero, CARAT should normally skip measuring; create a deterministic unit test for this case.

### 8.4 Twin correction and second decision

If observing: receive one noisy reading from `SensorGateway`, decrement budget **exactly once**, update twin state/variance, repeat candidate evaluation and PPO recommendation on corrected state, then pass the proposed action through risk constraints. If not observing, use existing belief and evaluate action without any hidden-state access. Record a human-readable decision trace with: before estimate, uncertainty, top plausible actions, regret, hypothetical VOI, cost, observation decision, observed value (only if requested), corrected estimate, action before/after, final action, and budget balance.

### 8.5 Crop-stage-sensitive risk manager

Implement `RiskManager.project(action, belief, stage, constraints)` returning `{proposed_mm, applied_mm, constraint_status, reasons, predicted_stress_quantiles, risk_flags}`:

- Hard guardrails: nonnegative daily action, configured max daily irrigation, no seasonal water overspend, bounded observation budget.
- Soft/model-based risk: estimate water-stress probability/quantile over plausible states for candidate action; reduce high-risk action when a feasible alternative exists. Weight stress cost by crop growth stage using crop-model documented parameters; do **not** invent guaranteed agricultural safety.
- Define and report the difference between **hard action constraints** and **uncertain agronomic risk estimates**.
- When no irrigation action satisfies all soft targets, return the best feasible hard-constraint action plus explicit unmet-risk warning.
- Ensure the risk manager cannot change the reference simulator state except through the approved irrigation action boundary.

### 8.6 CARAT pseudocode — implement this control flow

```python
# Illustrative interfaces; adapt to actual typed classes.
def decide_one_day(twin, ppo_policy, carat, sensor, limits, forecast, day):
    belief = twin.predict_from_available_information(forecast, day)
    initial_action = ppo_policy.predict(belief.to_agent_observation())
    regret = carat.estimate_expected_regret(belief, initial_action, forecast)
    voi = carat.estimate_value_of_observation(belief, forecast, regret)

    observe = (
        voi.net_value > carat.config.observe_threshold
        and limits.observations_remaining > 0
        and sensor.is_available(day)
    )
    if observe:
        measurement = sensor.take_measurement(day)  # budget charged atomically
        belief = twin.correct(measurement)

    proposed_action = ppo_policy.predict(belief.to_agent_observation())
    result = carat.risk_manager.project(proposed_action, belief, limits)
    return DecisionTrace(
        day=day, observe=observe, regret=regret,
        value_of_information=voi, before_action=initial_action,
        after_action=proposed_action, applied_action=result.applied_mm,
        remaining_budget=limits.snapshot(), risk=result,
    )
```

**Execution order:** determine action and observation using current legitimate information -> apply final irrigation -> advance hidden farm with realized daily weather -> log metrics -> expose *past* observed weather next day. Never evaluate an observation with access to the true state before deciding whether to observe.

### 8.7 Required ablations

1. PPO with no CARAT observation selection.
2. PPO + fixed-interval observation and correction.
3. PPO + random observation with matched budget.
4. PPO + pure uncertainty threshold observation.
5. PPO + counterfactual-regret observation **without** risk manager.
6. PPO + CARAT without belief correction (diagnostic only; explain interpretation).
7. Full PPO + CARAT + twin correction + risk manager.

Use the *same* training setup and held-out scenario/test budgets across observation policies. Where the baseline has different information access (e.g. ideal daily observations), label the comparison explicitly as an upper-information reference rather than a matched-budget baseline.

## 9. Training, evaluation, scientific metrics and tests

### 9.1 Research protocol

- Use chronological **season-level** 60/20/20 split when there are enough historical seasons; if few, use documented rolling-origin folds. Never split individual days at random across sets or train on test-season future realized weather.
- Validate on **real historical weather with simulated field** and on controlled synthetic stress tests. Distinguish both sources in dashboard and reports.
- Use multiple RL seeds (at least 5 for full research runs if resource budget permits), shared weather/scenario seeds, and paired comparisons. Report average, spread, and confidence intervals (bootstrap paired run differences, with limitations of small samples).
- Evaluate multiple observation budgets `5, 10, 20, 40` per season and sensor noise levels `0.01, 0.02, 0.04 m³/m³`, as starting experimental settings.
- Test a range of irrigation water limits and plausible soil configurations. Optimize irrigation-action and observation thresholds on validation only.
- Run model mismatch trials (reference AquaCrop vs approximate training soil model) and document that state-estimation corrections cannot eliminate structural model error.
- A fresh run creates immutable config + artifact manifest; no overwriting earlier results or changing statistics after export.

## 11. Worker design, resource controls and no-cost running

Use a **separate durable local worker process** and SQLite-backed job rows with strict transitions:

```text
queued -> running -> succeeded
                -> failed
                -> cancelled
queued -> cancelled
running -> interrupted (unexpected worker shutdown; resumable only if validated)
```

Only worker owns heavy computation and artifact write paths. API enqueues and reads metadata. Use atomic claim/heartbeat or lease mechanism; handle unexpected worker death at startup; never run the same job twice without idempotency strategy. Allow `max_parallel_training_jobs=1` by default, bounded cpu cores/time/memory where possible, and `max_parallel_simulation_jobs` configurable. Progress message design: `{sequence, job_id, status, phase, current_step, total_steps, metric_name?, metric_value?, timestamp, message}`. Estimate time only from actual observed progress if needed; never claim a task finished until artifacts are persisted and validated.
